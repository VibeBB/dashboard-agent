# Dashboard workflow

The workflow starts from an explicit device contract and ends with a verified,
reviewed handoff. A pass from the deterministic gates is authoritative;
decision, impression, and vision records explain choices but cannot turn a
failed gate into a pass.

| Stage | What happens | Primary agent | Tools and inputs | Records and outputs |
| --- | --- | --- | --- | --- |
| `contract` | Identify device telemetry/commands and physical interfaces; bind a firmware contract if available; declare protocol, transports, routes, caveats, widgets, hazards, session policy, and optional shell/WASM/WebMCP. | `dashboard-architect` | User brief, photos/sketches, firmware artifact; `dashboard_validate`, `dashboard_matrix`, `dashboard_check`. | Authored `.dash.json`; a decision for each meaningful design choice; `contract` stage impression. |
| `generate` | Project the validated contract into the application, runtime configuration, protocol artifacts, and optional Tauri scaffold. | `dashboard-developer` | `dashboard_generate` or `python -m dashboard generate`; contract is the only source input. | `out/<name>/` with `dash-manifest.json`; `generate` stage impression bound to final artifacts. |
| `gates` | Run static checks first; run full toolchain, runtime, WASM, Chromium, screenshot, and applicable Servo checks for a release/handoff-quality result. | `dashboard-developer`; independently checked by `dashboard-review` | `dashboard_check`, `dashboard_gates`, `dashboard_doctor`; generated app and pinned image. | Static/full `.dash-report.json` and `.dash-report.md`; `gates` stage impression after final regeneration. |
| `visual-review` | Inspect desktop/mobile screenshots, any Servo render, and user-supplied device/intake images against the contract and intended user task. | `dashboard-review` | `dashboard_screenshot`, `dashboard_gates`, `dashboard_smoke`, image viewer, intake manifest. | `.screens/desktop.png`, `.screens/mobile.png`, optional `servo.png`; one `dashboard_record_vision_review` per viewed image; `visual-review` stage impression. |
| `liaison` | Triage every dashboard-targeted UX request. Re-read stale inputs, ask questions through the response payload, and answer with evidence and gates. | `dashboard-architect` | At session start call `dashboard_ux_inbox`; use `dashboard_ux_respond` only to create/update responses. | `<id>.ux-response.json`; response cites VRP event IDs and report artifacts; `liaison` stage impression. |
| `handoff` | Present the contract, generated application/scaffold, protocol projections, gate outcome, screenshots, unresolved risks, and next steps. | Architect coordinates; developer and reviewer contribute | `dashboard_records_status`, report artifacts, screenshots, and generated README. | `handoff` stage impression and a concise evidence-based summary. |

## Stage rules

- Validate before generating. Static gates report contract and safety errors
  without requiring the full browser toolchain.
- Regenerate after a contract change, then rerun gates and review the final
  generated bytes. A fresh stage impression must hash the final artifact state.
- Every non-trivial decision should capture first principles, at least two
  options, evidence, assumptions, unknowns, residual risks, and a revisit
  trigger.
- Review what the dashboard means to a person operating the device, not just
  whether the page renders: correct labels/units, visible connection state,
  distinguishable hazardous controls, and a clear unsupported-platform message.
- A `done` liaison response requires a passing full report, current inputs,
  completed dependencies, at least one decision event ID and one impression or
  vision-review event ID. The actual deterministic report remains the source of
  gate truth.
- User device photos or sketches are not firmware facts. If the evidence does
  not establish a protocol or unsafe behavior, ask rather than inventing it.

## Typical command flow

```text
/dashboard:design
python -m dashboard validate <contract>
python -m dashboard generate <contract>
python -m dashboard check <contract>
python -m dashboard gates <contract> --out <out-dir>
python -m dashboard screenshot <contract>
python -m dashboard smoke <contract>
python -m dashboard record status
```

The slash command delegates contract authoring to the architect. In an
installed plugin, commands run through the launcher and Docker-default tools
image; direct host execution is a developer-only opt-in.
